## 1. What do Export-HelloID.ps1, HelloID-UX-improvements.user.js and HelloID-Entra-certificates.user.js do today; endpoints, authentication, export envelope, secret masking

### Takeaway
All three are Provisioning-only. Auth is the admin session in every case: the PS1 logs in with a local admin account and takes the portal's Bearer token; the main userscript rides the logged-in browser and copies the headers HelloID's own XHRs send to the provisioning gateway; the MCP server (section 3) gets cookies from a Chrome login. Every export file is JSON with a header `{exportedAt, exportedFrom, exportedBy, contents}`; `contents` is the kind discriminator (target systems are the one exception, recognised by shape). Secrets are masked as the string `***` by a shared name regex plus password-type form fields, controlled by one switch (`exportSecrets` / `-IncludeSecrets`).

### Inferences
- The envelope `{exportedAt, exportedFrom, exportedBy, contents}` plus one type-specific key (`rule`, `policy`, `schedule`, `customEvent`, `system`, `configuration`, ...) and name lists next to IDs (`systems: [{systemId, displayName}]`) is the repeating pattern; new SA kinds (e.g. `delegatedForm`, `automationTask`, `product`, `userDefinedVariable`, `directory...`) should add a `contents` value, a type key, and name companions for cross-references (forms to tasks/categories/groups, products to forms/groups).
- The existing auth plumbing assumes one API origin (the provisioning gateway) with a Bearer JWT audience `helloid.services`. The PS1 and MCP both discover it from `/server/v2/bootstrap/provisioning`. Whether SA pages use the same gateway, a same-origin `/api/v1`-style host, or a different bootstrap is not answerable from this repo.
- The userscript's gateway sniffing only fires on hosts containing "gateway"; if SA pages call same-origin endpoints with cookies, the sniffing in `proto.send` will never set `gateway` there and a second transport (same-origin fetch with cookies, or a different header capture) is needed.

### Gaps
- The SA admin API surface (paths, auth style) is not in the repo; no recordings exist (`gitignored/` is empty).
- Whether SA exports can reuse the portal Bearer token (`aud helloid.services`) is unknown from the code. The user memory note says Provisioning has no API-key auth and the admin session is the only route; whether that holds for SA is unverified here.

## 2. Userscript UI structure: tables, columns, Import buttons, backups on import, Overwrite all, caching, data fetching; where a 5th column on /admin/delegatedforms/ and a 6th on /admin/selfservice/products/ would go

### Takeaway
The userscript has no pattern for inserting a real column into an existing HelloID table. It decorates: buttons in AG Grid header cells and cells, copy buttons pinned inside cells, tile buttons, and (for the target system tiles) a hidden-source/own-table "list view". Everything is wired by one page-wide MutationObserver that calls idempotent `add*()` functions on every DOM change. Routing is by `location.hash`; SA pages (`/admin/delegatedforms/`, `/admin/selfservice/products/`) are path-based per the task statement and have no route constants, grid selectors or data hooks here.

### Inferences

## 3. helloid-mcp/: architecture, config and flags, write gating, tool registry, plan/apply contract, audit, kinds.ts, import classification, DryRun static check, environment handling, tests; how separate SA / Delegated Forms / Security / Settings flags fit

### Takeaway
A local Node/TypeScript MCP server (Streamable HTTP, loopback only, static bearer secret) that holds in-memory admin sessions per configured environment and exposes tools named `helloid_<verb>_<thing>`. Authorization is a single per-environment `mode` (`read|plan|write`) plus boolean `allow*` flags, resolved in one function (`refusalReason`) keyed by an `Access` string on each tool. A new flag is touched in about eight places (listed below). Writes always go plan -> apply with fingerprints, lock and before/after audit. Everything is ported from the userscript and is hard-wired to the provisioning gateway.

**Plan-then-apply contract** (`safety.ts:264-373`, `tools/import.ts`, `tools/delete.ts`)
- `PlanStore`: plans in memory, UUID, bound to environment + MCP session + `kind`, fingerprints (SHA-256 of canonical JSON) of every touched item, TTL 30 minutes, applied at most once (`PLAN_TTL_MS`). `get()` rejects missing/expired/applied/other environment/other kind/other session; `verify()` re-compares fingerprints ("HelloID changed since the plan; plan again") and drops the plan; `markApplied()` is called before running.
- `EnvironmentLocks.run(environment, work)` serializes writes per environment (`safety.ts:379-403`); `helloid_apply_plan` runs inside it, calls `verify`, `markApplied`, then `runImport`, records before/after per touch via `call.recordChanges` (`tools/import.ts:360-418`).
- Delete: `helloid_plan_delete` (kind + id; reads item and HelloID's own pre-checks) -> `helloid_apply_delete` (planId + `confirmName` equal to current name); needs mode `write` + `allowDelete`; `DELETE_KINDS` limited to seven provisioning kinds (`tools/delete.ts:19-28`; request/check table DESIGN.md:330-342). - Import: `helloid_plan_import` (access `plan`) takes `files:[{name,content}]` and `answers`; returns entries, choices (open decisions with options/defaults, no plan ID until answered), overview and plan ID; `helloid_apply_plan` (access `write`). - Dialogs are replaced by `answers`; backups before write are NOT ported (the user makes daily exports) (`planners/index.ts:1-9`, DESIGN.md:248).

**How separate flags for SA / Delegated Forms / Security / Settings would fit (inference from the structure)**
- Pattern A, mirror existing flags: add booleans to `environmentSchema` (e.g. `allowServiceAutomation`, `allowDelegatedForms`, `allowSecurity`, `allowSettings`, default false, as the existing write flags), extend `Access` and `ACCESS_FLAGS` so each requires mode `write` AND its flag (exactly how `delete/retryActions/approveBlocked/enforce` work), add them to `environmentInfo` (`tools/session.ts`), `cli.ts formatStatus` and the README/DESIGN tables. Read tools stay `access:'read'` (mode-gated only), consistent with how every provisioning read is gated; if sensitive reads are wanted (Security/Settings may hold secrets, users, roles), a `read`-style flag would be new behaviour (not present today; `evaluate` and `dryRun` are the only flags that gate non-write actions).
- Pattern B, per-area plan kinds: `PlanStore` already scopes plans by `kind`, so an SA plan kind (or the shared `import` kind with area-specific planners) can be added; `requireAccess` for the apply tool can be a different `Access` per area. Because `helloid_apply_plan` has a single `access:'write'`, mixing SA and Provisioning entries in one import plan would need either area-specific apply gating inside the handler (like `requireRevokingRulePublish` is called inside tool handlers) or separate plan/apply tools per area.
- Environment shape: today an environment is one portal with one gateway. If SA lives on the same `baseUrl` but another API origin, `EnvironmentSession` and `HelloIdClient` need a second origin/transport; per-area flags do not solve that.
- `safety.readOnly` currently overrides only the mode; flags that need mode `write` are automatically off under it, flags like `allowDryRun`/`allowEvaluate` are not. New SA flags that execute things (running a delegated form or automation task) would be in the second category and need an explicit decision.

### Inferences
- The least surprising extension is: new `KINDS` entries + planners for SA objects, new tool groups (`serviceAutomationTools`, ...) in `TOOL_GROUPS`, new `ACCESS_FLAGS` entries, new endpoint constants (`GATEWAY`-style) in `endpoints.ts`, new fixtures and routes in tests, and an equivalence-test harness extension if the userscript gets the same kinds.
- Since the server hard-wires the provisioning gateway discovery (`discoverGateway`), login detection (token endpoint 200), and `session.gateway`, an SA backend that is not behind the same gateway means a session/client change before any tool work.
- DESIGN.md describes itself as the agreed spec ("Everything in this document was agreed with the user", `DESIGN.md:5`; unknowns section `:353-372`; "Anything else not in this document or in the userscript: stop and report it instead of guessing an endpoint" `:372`), so SA scope is a design-doc change first.

## 4. README / CHANGELOG conventions (versioning, documentation style)

### Takeaway
Versions are date-based (`YYYY-MM-DD.N`), kept identical in the userscript `@version` and `Export-HelloID.ps1` `$ScriptVersion` when both change, and used as CHANGELOG headings, newest first. Docs are plain, user-oriented prose in English, with feature sections in the root README mirrored by a CHANGELOG entry; the MCP server has its own README and DESIGN.md and is not yet mentioned in the root README or CHANGELOG.

### Cited Findings
- Version format: userscript `// @version 2026-11-20.1` (`HelloID-UX-improvements.user.js:3`); PS1 `$ScriptVersion = '2026-11-20.1'` (`Export-HelloID.ps1:103`) and `$ExportedBy = "Export-HelloID.ps1 $ScriptVersion"` (`:104`); Entra companion has its own `2026-10-21.3` (`HelloID-Entra-certificates.user.js:3`). Tampermonkey auto-updates via `@updateURL`/`@downloadURL` on `raw.githubusercontent.com/Master-Guy/HelloID-UX-improvements/refs/heads/main/...` (`:4-5`, README.md:11-13). The version is written into exports (`exportedBy`) and into the migration handoff/tool file names and comments (README.md:73-79, CHANGELOG.md:100-105).
- CHANGELOG.md: header explains "Changes ..., newest first. Each heading is the script version that Tampermonkey shows. Versions that only changed the script's details (name, address, comments) are not listed." (`CHANGELOG.md:3`). Headings `## <version>` (`:5`, `:13`, `:19`, `:48`, ...); sub-headings `### <feature title>`; bullets with bold lead-ins (`**Menu:**`, `**Page buttons:**`), a `### Fixes` / `### Other changes` section where needed; user-facing wording, mentions menu item and setting names verbatim (e.g. **Target system export: include secrets**), and cross-names `Export-HelloID.ps1` with its version when it changed too (`:9-11`). Dates are consecutive with a `.N` counter for several releases a day (`2026-11-12.1/.2/.3`). The latest top entry is 2026-11-20.1. The MCP commit (b7d787e, 2026-11-24) did not touch CHANGELOG.md or README.md (git show --stat HEAD: only `.gitignore` and `helloid-mcp/*`).
- README.md: top-level `# HelloID UX improvements`, sections `## Installation`, `## Features` with one `###` per feature (target system filters, business rules filters, copy buttons, export/import per type, partial files, Import any export file, Overwrite all, Export everything, Clone, password eye, GitHub create, Entra certificates, Export without a browser (PowerShell), Settings). A parameter table documents `Export-HelloID.ps1` (`README.md:259-273`: Parameter | Subfolder | What a file has) and a table lists page-by-page imports (`:162-172`: Page | Imports). Tone: short declarative sentences, bold for choices/warnings, secrets and personal data warnings stated every time, "starts disabled" / "saved as draft" safety statements stated explicitly. README says it is a Provisioning interface improvement script ("quality-of-life improvements to the HelloID provisioning interface", `:3`), so SA scope would change its framing.
- helloid-mcp docs: `helloid-mcp/README.md` (tool table with a "Needs" column naming the mode/flag, setup, permissions JSON for `mcp__helloid__<tool>`, audit log, development) and `docs/DESIGN.md` (agreed spec incl. "Unknowns (find out, do not guess)" list). The tool table in README lists each tool name; the permissions block lists allow/ask tools; new tools must be added to both. Docs are plain markdown; DESIGN uses "Do not add features, flags or behaviour that are not described here" (`DESIGN.md:5`).
- Line endings: repo files are CRLF (`file` reports CRLF for README, CHANGELOG, PS1, userscript; `git config core.autocrlf` is true; `helloid-mcp/.gitattributes` `* text=auto eol=crlf`).
- Commit style (git log): short imperative English subject lines, no prefixes (e.g. "Mask notification secrets in target system exports", "Business rules: filter on entitlements and persons", "local MCP server v1 (provisioning only)"); the last commit's subject says "(provisioning only)", signalling the scope is expected to widen.

### Inferences
- A change to the userscript that is user-visible needs: bump `@version` (and `$ScriptVersion` if the PS1 changes), a new top CHANGELOG entry with the same version, a README section (and parameter-table row if PS1 gets a parameter), and for MCP changes an update of `helloid-mcp/README.md` tables plus `docs/DESIGN.md`.
- Because the MCP exporter uses `exportedBy: 'helloid-mcp 0.1.0'` (`index.ts:27`, `:87`) and has its own version, SA exports from the MCP server would carry that string; there is no CHANGELOG for the MCP package.

- Whether the `HelloID-Entra-certificates` version is bumped independently by a rule is not documented (it simply differs: `2026-10-21.3`).
