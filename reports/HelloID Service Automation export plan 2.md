# Extending HelloID tooling across three transports

The Service Automation (SA), Directory, Security and Settings areas can be added to the userscript, `Export-HelloID.ps1` and `helloid-mcp`, but not through the single-gateway design the three components share today. Live observation on the Training tenant shows that the admin UI uses **four different transports**: JSON on a per-module SA gateway origin (discovered through `//api/v3/sa/url/<module>`), JSON under `/server/v2/...` and a few `/api/v1/...` paths on the portal host, legacy ASP.NET MVC pages on the portal host (Kendo `getall` grids and server-rendered HTML forms with anti-forgery tokens), and an iframe on the identity host for 2FA. The two "last used" columns are the cheapest deliverable. Both grids are AG Grid driven through the grid API, both have verified GUID fields on the rows, and the activity and request-history list endpoints are known, so the first phase is confirmed feasible once one response body per endpoint is captured. About **half of the object families have no public API path** (checked against the local spec, 35 paths), so the admin session is the only route for them. Settings and most Security pages have no JSON at all: reading means fetching HTML and parsing form inputs, and writing means a form POST with a fresh anti-forgery token. **Four secret surfaces were observed** and all must be masked: the Entra SCIM secret (cleartext on a page), the API key Note column (pasted key and secret), IdP client secrets (plain text inputs) and the API key secret (password input, but present in the page HTML). The roadmap therefore starts with a transport phase, ships the columns second, exports third, and leaves lockout-prone Security imports and HTML-form Settings imports last.

Sources for this report are the project's own live-capture notes of 2026-11-24 (Training tenant, product version 2026.11.259170, read-only, no response bodies, no tokens): `research_notes/HelloID admin endpoint capture/` (three files), `research_notes/HelloID Service Automation export plan/live_capture_round1.md`, the earlier desk research in the same notes folder, and `gitignored/HelloID_Original.yaml`. These are local notes and carry no URLs. The earlier community-code and documentation citations are retained where they are still relevant. Everything marked "unverified" below was inferred, not observed.

Three further consequences affect the existing code and were not visible before. First, the userscript captures only headers of requests whose **hostname matches `/gateway/i`** (line 409 of `HelloID-UX-improvements.user.js`) and keeps a single `gateway` object. The SA gateway host name (`service-automation-training-we.helloid.cloud`) contains no "gateway", so the existing capture would never learn the SA origin or its headers. Second, the userscript `@match` lines already cover `*.helloid.com` and `*.helloid.training`, so the portal pages load the script, but the identity iframe (`helloid.cloud`) does not and cannot be reached from the parent page. Third, hash-only route detection (`location.hash.includes(...)`) does not fit the path-routed `/admin/...` URLs.

## Transport and authentication per component

### Userscript

The userscript is the best-placed component because it runs inside the logged-in page and needs no credentials of its own. It reads same-origin data with `fetch` and the cookie session (the HTML pages for Settings and Security, and the `/server/v2` and Kendo endpoints on the portal host), and it needs the Bearer header only for SA gateway calls. Three changes are required. The header-capture predicate must also match the SA gateway origin, and it must store **one captured origin and header set per origin** instead of a single `gateway`. A better source for the origin is the portal call `//api/v3/sa/url/<module>` that the page makes itself, read through the same intercept the script already uses. Route detection must work on `location.pathname` as well as the hash, because `/admin/delegatedforms/` and `/admin/selfservice/products/` are path-routed (Angular SPA), while Settings and Security pages are full page loads that never re-enter the SPA. Third, injected import buttons on MVC pages need their own insertion points, because those pages are not Angular. Whether the portal `/server/v2/admin/*` calls need the captured Bearer header or accept the cookie alone is not verified, so the captured headers should be sent to both hosts. Access to every admin feature stays permission-restricted by HelloID rights; per the user's decision it has no configuration flag. Reads must degrade silently (column hidden) on 401 or 403, as the earlier plan already required. The 403 seen on the data source list shows that failures happen even for an admin, so every new fetch needs that handling.

The userscript cannot reach the 2FA iframe (cross-origin) and should not try. 2FA and OATH are report-only: the exporter can note "not exported" and link to the page.

### Export-HelloID.ps1

The script logs in at `/authentication/admlogin`, takes a JWT from `/server/v2/security/token` and discovers the provisioning gateway from `/server/v2/bootstrap/provisioning`. For SA it needs (1) per-module discovery through the portal `//api/v3/sa/url/<module>` call (with the double slash, as observed), caching one origin per module, (2) a check whether the same JWT is accepted by the SA gateway (preflight suggests an Authorization header, but the token audience is unverified), (3) for `/server/v2/admin/*` and Kendo `getall` endpoints, whether the JWT or the login session cookie is accepted, and (4) an HTML reader that keeps the login cookie jar, fetches the page, and extracts `<input>`, `<select>` and `<textarea>` values by name. The reader must **drop** the anti-forgery token, the API key secret input, SCIM secret and any password-type value before anything is written. Kendo `getall` methods (GET or POST) and body shape are unverified; the PS script should send the same query keys the page sends (`take, skip, page, pageSize, virtual`, plus a cache-buster).

### helloid-mcp

`EnvironmentSession` and `HelloIdClient` hold one `gateway` origin. They need a map of origins keyed by role: provisioning gateway, SA gateway per module, portal (JSON and HTML), and a read-only note for the identity host. They also need an HTML-page reader with the same stripping rules as the script, and form-POST support for Settings and Security writes that fetches a fresh token per post and re-posts the **entire** form (every field and every MVC hidden checkbox twin, with changed values only patched), because a partial post would blank other settings. The MCP test harness needs fake-portal routes for the SA gateway and HTML pages. Writes to Settings, Security and Directory pages are the highest-risk operations in the project and should land last.

## The columns: what is ready and what is still blind

"Last used" counts **submitted forms only**, so it reads the activity endpoint, filters rows where the Submission value is "Submitted" and keeps the maximum start time per form GUID. "Last requested" reads request history for **every status including cancelled and denied** and keeps the maximum request time per product GUID. Both reduce one aggregated fetch to a `Map(guid -> max timestamp)` cached about five minutes and cleared on navigation, which fits the existing `INTERCEPTS` and `WATCHES` pattern. The activity page's Submission and Task state filters suggest the filter might be requested server-side through `searchFields`, but that is unverified, so the safe design fetches all rows and filters client-side.

Injection is settled by the DOM notes. On `/admin/delegatedforms/` (4 columns: Icon, Name, Status, Actions) and `/admin/selfservice/products/` (5 columns: Icon, Name, Description, Visibility, Actions) the userscript's `findGridApi` already returns a working API, and a plain-JS `cellRenderer` in an appended column definition coexists with the Angular framework renderers. The recommended rules are: call `setColumnDefs` once per grid API (keep a WeakSet), re-apply when `getColumnDefs()` no longer contains the column id after a route change, key the join on `data.id` (forms) and `data.selfServiceProductGuid` (products), never select by `col-id` or `_ngcontent-*`, and use `api.refreshCells` when the map arrives after the first render (the infinite row model renders before the aggregate fetch finishes). Sorting should stay disabled on the new columns: the forms grid pages server-side (20 per page via `getallforgrid`) and the products grid has no sortable columns, so a client-side sort would only reorder one page.

Two caveats limit the claim of "ready". The retention of both lists is unknown; the empty-state text should read "No activity in the retained history", never "never used", and the column should expose the oldest timestamp seen. And the join key on the **request history** side is unverified: if those rows carry only a product name, renamed or duplicated product names produce false misses, which needs one response body to rule out. The Training tenant holds a single activity (one form, one date) and no request-history sample is documented, so even the body capture should preferably come from a tenant with sample data.

## Phased roadmap, import order and risks

Phase 0 is transport: multi-origin discovery in all three components, pathname routing in the userscript, an HTML reader, and a **DESIGN.md update first**, because DESIGN.md forbids features, flags or behaviour not described in it. Phase 1 ships the two columns (read-only, no flags, lowest risk), after the activity and history bodies are captured. Phase 2 is SA read and export: delegated forms and categories, dynamic forms (shared, so deduplicated), data sources, products (with new and legacy actions), self-service categories, approval workflows, then variables, scripts, tasks and automation systems, with `***` for secret variables and `hasValue`. Phase 3 is SA import (plan-then-apply with automatic backups), blocked until the save requests are captured. Phase 4 covers Directory and Applications: Local groups and Local users, mapping sets, agent pools (verify only), application categories and applications. Phase 5 covers Security and Authentication, export first and import last behind lockout guards. Phase 6 covers Settings: Appearance, Language, Company, Logging, Certificates (metadata only, read-only).

The **import order**, derived from references and not documented by HelloID, is: variables, agent pools (verify), groups, mapping sets, Local users (managers first), group membership, automation tasks and scripts, data sources (task-backed after their task), dynamic forms (remap data source GUIDs), self-service and delegated form categories, approval workflows, application categories, applications, products (then groups, actions and segregation), delegated forms (then categories and the task, whose object GUID is the new form GUID), roles, then identity providers, access rules and policies. Certificates referenced by applications and IdPs are a pre-check, never an import step.

**Lockout risk** is unchanged and gets sharper. Portal access rules, IdPs, sign-on lock settings, mobile app and 2FA settings can lock admins out, and the documented recovery is a call to support ([Tools4ever blog](https://www.tools4ever.com/blog/access-management-context-based-access)). Deny beats permit and the Local IdP cannot be disabled ([Portal access rules](https://docs.helloid.com/en/identity---authentication/security/portal-access-rules.html)). Safeguards: never delete rules, roles, IdPs or keys; refuse any apply that leaves no usable IdP or matches the running admin with a deny rule; never change IdPs and access rules in one run; treat built-in roles, the Local IdP and system roles as read-only; and warn on lockout count, session timeout and remember-me. The roles list shows built-in and custom roles together, and the rights tree has no captured grouping, so role import stays export-only until the structure is known.

**Secret risk** now has observed instances. Masking must be done **at read time, in every component**, because some secrets reach the client without being displayed: the API key secret sits in the HTML in a password input; IdP client secrets and the "on behalf of" secret are plain text inputs; the Entra page shows the SCIM secret in cleartext; the API key Note column contains pasted credentials. Variables with the secret flag display as masked dots in the UI, but what the endpoint returns is unverified. Secret-shaped inputs (password type or names matching the existing `SECRET_NAME` pattern) get `***`, and a `***` on import means "keep the existing value". The Note column and any free-text field (custom text, custom CSS, script bodies) get a scan with the same patterns and a warning that inline secrets cannot be reliably detected. Certificates are metadata only; the PFX export includes the private key and is never called. OATH seeds are never exported. Directory users export carries personal data and needs the same warning as the excluded-persons export. Local user import cannot carry passwords; how creation behaves without one is unverified and import should be postponed until it is.

**GUID remapping risk**: GUIDs are server-generated and no seen endpoint accepts a client GUID. Match by name (variables, groups, categories, data sources, forms, pools, workflows) and remap every reference, including data source GUIDs embedded in dynamic form schemas, access groups on delegated forms, resource owner group and approval workflow on products, and manager GUIDs on users. A same-tenant restore after deletion also loses history linked to the old GUID, and the column maps are keyed on GUID, so a restored form restarts at "no activity". The plan output must state this. Whether the schema embeds task, form or product GUIDs beyond data sources is unknown.

**HTML-form POST risk**: Settings and most Security pages post `application/x-www-form-urlencoded` to the same URL with `__RequestVerificationToken`. The safe pattern is to GET the page immediately before, parse the whole form (including the six GUID-named Appearance toggles whose meaning is unknown), patch only the fields in the import file, and post everything. Reset buttons (Reset custom styling) and anything that calls Download, Reset password, Reset second factor, Force Synchronization, Generate secret or Delete secret must never be invoked by tooling. Appearance images are uploaded through a widget whose endpoint is unobserved; the hidden values are 32-character ids, and the preview points to the CDN. Image export (a GET of the CDN URL, if public) is plausible. Image import is blocked on the upload capture. Tenant-bound settings (custom domains, mail domain, default AD domain, redirect URLs, service desk and incident addresses) are skipped by default.

## Configuration flags: separate read, write, run and backup

The user's decisions fix the scheme. MCP **reads are flag-gated as well as writes**; the browser userscript and the API are only permission-restricted; **run-flags are separate** from read and write. The existing mechanism (booleans in `environmentSchema`, `Access` and `ACCESS_FLAGS` in `safety.ts`, a flag requires mode `write` plus its own boolean) extends to this. The proposal is one read flag and one write flag per area, all default false, with write implying read (a write flag without its read flag is rejected at config load):

| Area | Read flag | Write flag | Covers |
|---|---|---|---|
| Delegated forms | `allowReadDelegatedForms` | `allowWriteDelegatedForms` | forms, categories, activity |
| Self-service | `allowReadSelfService` | `allowWriteSelfService` | products, categories, approval workflows, request history |
| Dynamic forms and data sources | `allowReadDynamicForms` | `allowWriteDynamicForms` | forms, data sources |
| Automation | `allowReadAutomation` | `allowWriteAutomation` | variables, scripts, tasks, systems |
| Agent pools | `allowReadAgentPools` | `allowWriteAgentPools` | pools (write limited to existing public API verbs) |
| Applications | `allowReadApplications` | `allowWriteApplications` | applications, categories |
| Directory | `allowReadDirectory` | `allowWriteDirectory` | Local users, groups, mapping sets |
| Security | `allowReadSecurity` | `allowWriteSecurity` | roles, access rules, policies, API config (report-only), 2FA (report-only), mobile app |
| Authentication | `allowReadAuthentication` | `allowWriteAuthentication` | IdPs, SMS, RADIUS |
| Settings | `allowReadSettings` | `allowWriteSettings` | Appearance, Certificates (metadata, no write), Logging, Language, Company |

Run-flags are a separate set, default false, **not switched off by `safety.readOnly`** in the same way `allowDryRun` and `allowEvaluate` are, and each needs its own explicit decision: `allowRunDelegatedForm` (submit or test a form), `allowRunAutomationTask` (Run Now), `allowRunDataSource` (test or execute a data source) and, if ever added, `allowRunProductAction`. Running anything passes through the project rule that every write in a script is guarded by DryRun and DryRun is never disabled; the existing `dryrun-check.ts` covers only target-system scripts, so SA scripts need either their own check or a rule that run tools only execute stored, unmodified tasks. `allowBackup` (create backups and read the backup store) and `allowRestore` (apply a backup) are separate again, and restore requires the relevant area write flag in addition. `allowDelete` stays the only deletion gate and `DELETE_KINDS` stays provisioning-only until SA delete pre-checks are captured. Where a read is flagged off, the tool is not registered at all (hidden), not merely refusing.

Because `helloid_apply_plan` has one write access, the cleanest audit is **per-area plan and apply tools**, or a handler check on the area flag as `requireRevokingRulePublish` does today. A change touches roughly eight places (`config.ts`, `config.example.json`, `safety.ts`, `tools/session.ts`, `cli.ts`, README tables, DESIGN.md, and the config and safety tests), plus a new kind in `ITEM_KINDS`, `IMPORT_ORDER`, `makePlanners`, `KIND_LABELS` and `Exporter.everythingParts()`. **DESIGN.md must describe the flag scheme before any code**, as it forbids undocumented flags. House conventions carry over: date-based versions (`YYYY-MM-DD.N`, identical between userscript and script), a user-facing CHANGELOG entry, a README section and parameter row, the `contents` envelope with one new value per family, `secretsIncluded` where relevant, CRLF line endings, and the marker lines the test harness slices on kept intact.

## What the user must still capture or do

Prioritised and de-duplicated. Nothing here requires pasting secrets; redact values to `<redacted>` and, for secret fields, state only whether the field is absent, empty, null, masked or clear text.

- **Priority 1: unblock Phase 0 and the columns.**

## Conclusion

The new knowledge flips the earlier plan's risk profile. The data model and mechanisms (envelope, masking, plan-then-apply, flags) were never the problem. The transport was, and it turned out to be four transports with a script-capture predicate (`/gateway/i`) that would silently miss the SA origin. Meanwhile the two requested columns became the best-understood work item in the project: the grids, the join keys and the injection technique are all verified, and only two response bodies stand between the plan and an implementation.

Security and Settings are harder than the earlier plan assumed but in a different way: they are not undocumented JSON, they are HTML forms with embedded tokens and, in four places, embedded secrets. This favours reading through the page HTML with strict stripping, treating every free-text field as possibly secret, and treating write as a whole-form operation rather than a patch. Export for every family can ship safely well before import, and the flag design (read-gated, write-gated, run-gated, backup and restore separate) gives each step a place to stop.
